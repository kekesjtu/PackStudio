# ADR-0001：采用 Web 前端与 Python 后端分离架构

## 日期

2026-07-11

## 背景

PackStudio 同时需要密集的引导式表单、三维矩形块预览、封装几何规则、材料计算和特定
XML 格式输出。界面迭代与模型规则的变化速度不同，并且模型生成能力未来可能被命令行或
批处理流程复用，因此需要明确 UI 与领域逻辑的边界。

## 决策

采用 React + TypeScript 构建单页 Web 前端，采用 FastAPI + Pydantic 构建本地 Python
服务。两者通过 REST/JSON 通信。所有几何、材料、热源、边界条件和导出规则放在与 Web
框架无关的 Python 领域层中。

首个交付形态为本机启动 FastAPI 与 Vite 开发服务；生产形态可由 FastAPI 提供前端静态
资源。是否增加桌面壳由后续分发需求决定，不在本 ADR 中预先绑定。

## 备选方案

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| React + FastAPI | 表单和三维生态成熟；Python 适合数值与 XML；领域层可复用 | 开发期需要协调两个工具链和本地端口 |
| PySide/PyQt 桌面应用 | 单语言后端；原生桌面集成直接 | Web 三维与组件生态难直接复用；UI 测试和发布成本较高 |
| Electron/Tauri + Python 服务 | 可提供安装包和桌面体验 | TASK1 阶段增加进程管理、签名和打包复杂度 |
| 全 TypeScript | 单工具链；类型可前后端共享 | 既有求解器接口、数值计算和工程团队的 Python 工作流利用不足 |

## 理由

1. 参数向导、组件树和实时三维预览是前端的主要复杂度，React 生态与需求匹配。
2. 模型生成、阵列计算和 XML 输出是后端主要复杂度，Python 的数值、校验与测试生态更合适。
3. 领域层与 API 解耦后，可在不启动浏览器的情况下完成批量生成和回归测试。
4. 先交付本地 Web 形态，能够推迟桌面打包这一可逆但昂贵的决定。

## 结果

- 仓库同时维护 npm 与 Python/conda 配置。
- API 对象不能直接替代领域对象；边界处必须校验。
- 前后端都需要独立的自动化测试，并在集成阶段增加契约测试。
- 将来若引入桌面壳，应新增 ADR，说明安装、升级、进程生命周期和文件权限策略。
